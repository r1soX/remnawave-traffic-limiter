# Установка интеграции Bedolaga и Paired WhiteList

Этот патч связывает Bedolaga с сервисом Remnawave Traffic Limiter. После его установки Bedolaga передаёт сервису актуальное состояние подписки, а сервис сам определяет, нужен ли технический WhiteList-пользователь. До установки патча завершите базовое развёртывание limiter и Caddy по [DEPLOYMENT.md](DEPLOYMENT.md).

## Совместимость

Текущая версия патча проверена с **Bedolaga v4.8.0**, commit
`1fe2b47a85724d320ec46ad76cfa336c688dd8f2` от 9 сентября 2026 года.
Патчер также сохраняет поддержку предыдущей структуры файлов, но перед
установкой на более новую версию Bedolaga сначала проверьте его на копии.

## Что меняет патч

- в личном кабинете отображается фактический лимит и расход WhiteList-трафика;
- после покупки, продления, смены тарифа, докупки трафика и изменения статуса Bedolaga передаёт полный целевой статус подписки;
- при тарифе только с Main основной пользователь получает его собственные лимит и сквады, а техническая WhiteList-пара отключается, но не удаляется;
- при возврате на тариф Main + WhiteList используется прежняя техническая пара — новые аккаунты не создаются;
- счётчик WhiteList сбрасывается только с началом нового расчётного периода, но не при смене тарифа или докупке трафика;
- обработка webhook-ов Bedolaga сериализуется, что предотвращает очереди из блокировок базы данных.

## Однократная установка

Распакуйте файлы патча **вне** репозитория Bedolaga. Тогда последующий `git pull` не удалит их.

```sh
mkdir -p <КАТАЛОГ_ПАТЧЕЙ>
unzip -o <АРХИВ_ПАТЧА>.zip -d <КАТАЛОГ_ПАТЧЕЙ>

cd <КАТАЛОГ_BEDOLAGA>
sh <КАТАЛОГ_ПАТЧЕЙ>/reapply_bedolaga_paired_whitelist.sh
```

Добавьте в `.env` Bedolaga следующие значения. Адрес limiter должен быть доступен из контейнера бота:

```env
PAIRED_WHITELIST_LIMITER_URL=https://LIMITER_PUBLIC_DOMAIN
# Тот же UUID, что WHITELIST_SQUAD_UUID в .env limiter.
PAIRED_WHITELIST_SQUAD_UUID=UUID_WHITELIST
# В точности совпадает с PAIRED_WHITELIST_CONTROL_TOKEN в .env limiter.
PAIRED_WHITELIST_LIMITER_TOKEN=СЛУЧАЙНЫЙ_СЕКРЕТ_УПРАВЛЕНИЯ
```

`PAIRED_WHITELIST_LIMITER_TOKEN` применяется и для чтения счётчика в кабинете:
бот обращается к `GET /api/pairing/<shortUuid>`. Поэтому отдельный
`DIAGNOSTICS_TOKEN` в `.env` Bedolaga не нужен.

`PAIRED_WHITELIST_LIMITER_URL` — публичный HTTPS-домен limiter. Не указывайте
в нём Docker-порт или внутренний адрес: бот может находиться на другом сервере.
На публичном прокси limiter должны быть доступны только `/webhook`, `/sub/*` и
`/api/pairing/*`; диагностические маршруты не публикуются.

Пересоберите только контейнер бота. Состав compose-файлов зависит от вашей установки:

```sh
docker compose -f <ОСНОВНОЙ_COMPOSE_ФАЙЛ> -f <ДОПОЛНИТЕЛЬНЫЙ_COMPOSE_ФАЙЛ> \
  up -d --build --no-deps <ИМЯ_СЕРВИСА_БОТА>
```

## После каждого `git pull` в Bedolaga

```sh
cd <КАТАЛОГ_BEDOLAGA>
sh <КАТАЛОГ_ПАТЧЕЙ>/reapply_bedolaga_paired_whitelist.sh
docker compose -f <ОСНОВНОЙ_COMPOSE_ФАЙЛ> -f <ДОПОЛНИТЕЛЬНЫЙ_COMPOSE_ФАЙЛ> \
  up -d --build --no-deps <ИМЯ_СЕРВИСА_БОТА>
```

Применение выполняется атомарно: перед запуском скрипт временно сохраняет все
затрагиваемые файлы. Если хотя бы один патчер или проверка синтаксиса завершится
ошибкой, исходное состояние будет восстановлено автоматически. Если новая
версия Bedolaga снова изменит ожидаемые фрагменты, обновите патч под неё, а не
применяйте изменения принудительно.

## Проверка после установки

1. Переключите тестового пользователя на тариф Main + WhiteList с лимитом.
2. Убедитесь, что в панели появилась не более чем одна техническая пара для этого пользователя.
3. Проверьте `GET /api/state/<SHORT_UUID>` на limiter: лимит и расход должны соответствовать WhiteList-пакету.
4. Переключите пользователя на тариф только с Main и убедитесь, что техническая пара стала `DISABLED`.
5. Верните тариф Main + WhiteList: должна активироваться та же техническая пара.
