# Установка патчей Bedolaga

Комплект связывает Remnawave Traffic Limiter с ботом и кабинетом Bedolaga. Он
передаёт limiter полный тариф пользователя, показывает фактический WhiteList-
трафик и объединяет устройства Main и технического WhiteList в одну логическую
подписку.

## Совместимость

Патчи проверены на точных исходниках:

- `remnawave-bedolaga-telegram-bot` **v5.0.0**, commit
  `5bda3c56f0afd9f4813e9c6fa48934948b05ebae`;
- `bedolaga-cabinet` **v1.80.1**, commit
  `a693d30ca6084b9a54b45a72294b99237841ef13`.

Патчер кабинета намеренно откажется работать с другой версией. Патчеры бота
проверяют ожидаемые фрагменты и останавливаются без частичного применения, если
структура новой версии изменилась.

## Что меняется

- лимит трафика, стратегия сброса, дата окончания, статус и сквады применяются
  как полное целевое состояние тарифа;
- переходы между Main, WhiteList и Main + WhiteList корректно возвращают лимит
  основному пользователю или включают техническую пару;
- при оплате, продлении или смене тарифа сброс трафика выполняется одновременно
  у Main и WhiteList;
- лимит устройств тарифа записывается и Main, и WhiteList;
- кабинет получает объединённый список устройств двух аккаунтов, удаляет
  дубликаты по HWID и считает одно физическое устройство один раз;
- переименование, удаление, удаление всех устройств и уменьшение лимита
  применяются ко всей логической подписке;
- при удалении Main из Remnawave технический WhiteList-пользователь удаляется
  автоматически, а связь пары очищается из SQLite;
- кабинет 1.80.1 показывает, что Main и WhiteList учтены вместе;
- webhook-обработчики сериализуются, чтобы снизить риск конфликтов блокировок БД.

Если limiter временно недоступен, управление устройствами остаётся доступным для
Main. После восстановления связи следующая тарифная синхронизация снова выровняет
лимит устройств.

## Рекомендуемый порядок для двух серверов

1. На сервере **Panel + Limiter** обновите и пересоберите limiter.
2. На сервере **BOT** обновите bot до v5.0.0, примените серверный патч и
   пересоберите контейнер бота.
3. Там, где развёрнут `bedolaga-cabinet`, обновите его до v1.80.1, примените
   UI-патч и пересоберите кабинет.
4. Проверьте тестового пользователя, затем включайте обработку всех пользователей.

Поле `hwidDeviceLimit` в управляющем API limiter необязательное, поэтому такой
порядок допускает поэтапное обновление без поломки старого бота.

## 1. Обновление limiter

На сервере Panel + Limiter:

```sh
cd <КАТАЛОГ_LIMITER>
git pull --ff-only
docker compose up -d --build --force-recreate
docker compose ps
docker compose logs --since 5m remnawave-traffic-limiter
```

Не удаляйте volume `/data`: в SQLite хранится соответствие Main и WhiteList.

## 2. Патч бота v5.0.0

Храните файлы патча вне репозитория бота, чтобы `git pull` их не затронул:

```sh
mkdir -p <КАТАЛОГ_ПАТЧЕЙ>
unzip -o <АРХИВ_ПАТЧА>.zip -d <КАТАЛОГ_ПАТЧЕЙ>
```

Проверьте версию бота:

```sh
cd <КАТАЛОГ_BOT>
git fetch --tags
git checkout v5.0.0
git rev-parse HEAD
```

Ожидаемый commit:

```text
5bda3c56f0afd9f4813e9c6fa48934948b05ebae
```

Примените патч из корня репозитория бота:

```sh
sh <КАТАЛОГ_ПАТЧЕЙ>/reapply_bedolaga_paired_whitelist.sh
```

Скрипт применяет патчи отображения, тарифной синхронизации, устройств и webhook,
после чего запускает `py_compile`. При ошибке он восстанавливает все затронутые
файлы из временного снимка.

Добавьте в `.env` бота:

```env
PAIRED_WHITELIST_LIMITER_URL=https://LIMITER_PUBLIC_DOMAIN
PAIRED_WHITELIST_SQUAD_UUID=UUID_WHITELIST
PAIRED_WHITELIST_LIMITER_TOKEN=ТОТ_ЖЕ_PAIRED_WHITELIST_CONTROL_TOKEN

RESET_TRAFFIC_ON_PAYMENT=true
RESET_TRAFFIC_ON_TARIFF_SWITCH=true
```

`PAIRED_WHITELIST_LIMITER_URL` должен открываться из контейнера бота. Не
передавайте боту `DIAGNOSTICS_TOKEN`: для чтения состояния пары используется
control token и маршрут `/api/pairing/*`.

Пересоберите только сервис бота, подставив реальные compose-файлы и имя сервиса:

```sh
docker compose -f <COMPOSE_1> -f <COMPOSE_2> \
  up -d --build --no-deps <BOT_SERVICE>
```

## 3. Патч кабинета v1.80.1

Проверьте версию кабинета:

```sh
cd <КАТАЛОГ_BEDOLAGA_CABINET>
git fetch --tags
git checkout v1.80.1
git rev-parse HEAD
```

Ожидаемый commit:

```text
a693d30ca6084b9a54b45a72294b99237841ef13
```

Установите зависимости и примените патч:

```sh
npm ci
sh <КАТАЛОГ_ПАТЧЕЙ>/reapply_bedolaga_cabinet.sh
npm run build
```

Скрипт добавляет типы ответа API, пояснение объединённого учёта устройств и
переводы ru/en/fa/zh, затем запускает `npm run type-check`.

Пересоберите сервис кабинета своей compose-командой:

```sh
docker compose -f <COMPOSE_ФАЙЛ> \
  up -d --build --no-deps <CABINET_SERVICE>
```

## Повторное применение после обновлений

После `git pull` файлы upstream могут быть заменены. Для тех же совместимых
версий просто повторите:

```sh
cd <КАТАЛОГ_BOT>
sh <КАТАЛОГ_ПАТЧЕЙ>/reapply_bedolaga_paired_whitelist.sh

cd <КАТАЛОГ_BEDOLAGA_CABINET>
sh <КАТАЛОГ_ПАТЧЕЙ>/reapply_bedolaga_cabinet.sh
```

Оба патча идемпотентны. Если upstream изменил ожидаемый код, не правьте проверки
и не применяйте патч принудительно — подготовьте новую совместимую версию.

## Проверка

1. Выберите тестовую подписку Main + WhiteList с конечным трафиком и лимитом
   устройств больше нуля.
2. Переключите тариф и проверьте в логах бота строку
   `Applied paired WhiteList tariff target`.
3. Проверьте состояние limiter:

   ```sh
   docker compose exec -T remnawave-traffic-limiter sh -lc \
     'wget -qO- --header="X-Limiter-Diagnostics-Token: $DIAGNOSTICS_TOKEN" \
     "http://127.0.0.1:${PORT}/api/state/TEST_SHORT_UUID"'
   ```

4. В Remnawave проверьте одинаковый `hwidDeviceLimit` у Main и WhiteList.
5. Подключите один клиент к обеим частям подписки: в кабинете он должен занимать
   одно место, даже если Remnawave зарегистрировал один HWID у обоих аккаунтов.
6. Удалите это устройство в кабинете и убедитесь, что HWID исчез у Main и
   WhiteList.
7. Уменьшите лимит устройств: лишние новые HWID должны удалиться из обоих
   аккаунтов, а число занятых мест не должно превышать новый лимит.
8. Выполните оплату или смену тарифа со сбросом и убедитесь, что оба нативных
   счётчика трафика стали нулевыми.
9. Удалите отдельного тестового Main-пользователя из панели и проверьте в логах
   limiter строку `paired user deletion completed`; технический WhiteList-
   пользователь также должен исчезнуть.

Для пилота оставьте `PAIRED_WHITELIST_MANAGE_ALL=false` и укажите тестовые UUID.
После успешной проверки можно включить `PAIRED_WHITELIST_MANAGE_ALL=true`.

## Откат

Патчеры создают файлы `*.before-*`. Для отката остановите контейнер, восстановите
нужные исходники из этих копий и пересоберите сервис. Более надёжный вариант —
вернуть чистый checkout точного тега, а `.env` и volumes оставить без изменений.

Никогда не публикуйте `.env`, API-токены, control token, реальные UUID
пользователей, IP-адреса или домены своей инфраструктуры.
